3. V4：三种 attention 的完整计算流程

下面三张图分别把 m=0 / m=4 / m=128 三条路径从输入到输出的每一步画全：token 怎么被选中、KV 怎么被压缩、分数与最大值怎么算、最后怎么用 KV 算出输出。行号对应本仓库 configs/official_inference 的固定版本，细节请回到源码复核。

3.0 三条路径总览：同一段历史的读取粒度

一段输入历史与当前步 q_t：先建立统一的 token 坐标，后面三种路径都对齐到它。

m = 0：只保留滑动窗口，更早的 token 完全不参与本层 attention。

m = 4：每 4 个 token 归为一组，组是后续压缩与检索的粒度。

每个组池化成一个压缩块 C0…C5 —— 历史被压缩，但块与 token 的对应关系保留。

Indexer 在“块”这一级做选择，只把 Top-K（此处 C1、C4）交给稀疏 attention。

m = 128：分组非重叠、粒度远粗，读取粗粒度长程历史并与局部 SWA 结合。

三条路径对比：压缩比越大，历史越粗，可覆盖的上下文越长；取值条件需回到该 commit 核验。

3.1 m = 0 · 纯滑窗 attention：逐 step 计算流程

起点：上一层 mHC 混合后的子层输入，形状 [b, s, dim]。

Q 先做低秩投影，再乘一个由自身 RMS 决定的缩放（等价于 QK-norm）。

把 RoPE 只加到 Q 的末尾 64 维上，nope 维保持不动。

KV 是单头共享的 MLA 潜向量，head 之间不各存一份。

非 rope 维走 FP8 模拟量化：先求每行绝对值最大值 amax，再据此定 scale —— 这是第一处「最大值」。

选 token 只取最近 win 个位置；窗口外的位置在索引里记为 -1，kernel 会跳过。

KV 写进环形缓存：decode 时按 start_pos % win 覆盖最旧槽，逻辑位置靠索引还原。

attention 的核心：分块做 online softmax，用运行最大值保持数值稳定，分母额外加上可学习的 attn_sink —— 这是第二处「最大值」。

最后反旋转去掉位置信息，再经分组低秩 O 投影回到 dim。

3.2 m = 4 · 重叠压缩 + Indexer Top-K：逐 step 计算流程

起点与 m=0 相同：上一层混合后的 hidden。

Q 低秩投影后留一份 qr —— 它会被 Indexer 复用去给压缩块打分。

主 KV 的投影、RoPE 与 FP8 量化与 m=0 一致。

压缩第一步：把每 4 个 token 用可学习权重池化成 1 个压缩块，重叠窗口让边界更平滑。

压缩块再经 norm、RoPE（用块位置）与量化，落到 kv_cache 的 win 之后那一段。

Indexer 有自己的一套压缩 KV：先 Hadamard 旋转再 FP4 量化，只用于打分。

打分：每头做点积、relu、再按可学习 head 权重求和，得到一个块级分数。

选块：对分数取 Top-K，被因果 mask 的块记为 -1，再加 offset 映射到 KV 坐标。

把「窗口 token 索引」和「Top-K 块索引」拼成一个数组，KV 池也相应合并。

最后是同一个稀疏 attention kernel：running max + attn_sink + 加权求和。

3.3 m = 128 · 粗粒度压缩 + 全量压缩块：逐 step 计算流程

同样的 hidden 输入，由该层的 compress_ratio 决定走 128 这条强压缩路径。

Q 的投影与归一化不变，但不需要留 qr 给 Indexer。

KV 投影与量化也不变 —— 三条路径的差别在压缩与选块，不在投影。

压缩粒度放大到 128：非重叠分组，用可学习权重池化，块与块之间不共享 token。

decode 时逐格累积状态，每满 128 步才池化并落一次缓存。

关键差异：没有 Indexer，所有已完成的压缩块都被读入，不做 Top-K 选择。

索引里只有窗口位置 + 全部粗块；因为块粒度粗，池子反而比 m=4 的候选集更短。

最终仍收敛到同一个 attention kernel：运行最大值保证稳定，attn_sink 进分母。

3.4 三处「最大值」分别在做什么

出现位置计算作用
量化 scaleamax = reduce_absmax(x, dim=1) → fast_round_scale逐行取绝对值最大值，据此定 FP8/FP4 的缩放系数，保证不溢出（三条路径都有）
Indexer 选块分数index_score = (relu(q·kᵀ) × weights).sum(heads) → topk把每个压缩块压成一个标量分数再取 Top-K；只有 m=4 有这一步
attention softmaxscores_max ← reduce_max(acc_s)（跨块不 clear）分块累加时保持数值稳定，并用 exp(max_prev - max) 回缩已累积结果；分母另加 exp(attn_sink - scores_max)

4. V4.1：CED、跨层共享与 CSA2 执行图

本地总结已覆盖 CED、Full/Reindex/Reuse、分层索引、Engram、DSpark、ViT 与 FP4 KV。以下图强调它们之间的依赖关系，而非把每个创新点孤立记忆。

4.1 Encoder 到 Decoder 的状态交接

输入先经文本 / 图像预处理与 Embedding / ViT 对齐，进入编码器。

前 20 层做因果编码，并把主 KV、Indexer K、候选块发布成共享状态。

共享状态汇入一条总线：它按 source layer 组织，而不是每个层各存一份。

后 20 层解码时消费这条总线（配合 bounded replay），交接点就在编解码边界。

解码结果进入 logits，并交给 DSpark 做投机解码验证。

读图要点：谁发布、谁消费由 source layer 决定，具体层数与分工随型号变化，必须核实。

请核实所讨论的 V4.1 型号和具体配置：CED 层数、候选块源层、KV/indexer source layers 均可能随模型版本变化。Flash README/config 与其他型号不能混用。

4.2 CSA2 三种模式：共享状态的生产者与消费者

Full生产主 KV / Indexer K，并从 query 构造稀疏选择；常作为一组共享状态的源头。
Reindex复用主 KV，重新计算索引选择；主要新增索引工作而不是重复存储所有 KV。
Reuse消费已生成的 KV 与 Top-K 选择，尽量避免重复索引；验证跨层复用的层映射和有效期。

补充区分：层级索引器候选池如何由 source layer 建立，块大小、候选 top-k 与最终 top-k 的关系；复杂度不能只看总 token 数，也要看候选池和共享策略。

8. Serving 请求生命周期：正常路径与回收/失败分支

请求先在 API 层完成校验、模板化与准入，并拿到 request slot 与 KV 预算。

进入引擎后是 prefill + 逐 step decode 的执行循环。

decode 不是一次性的：采样后回到批处理，开始下一个 step。

正常结束走 EOS / 长度上限 → flush 流式输出并释放状态。

中断路径（取消 / 超时 / OOM）从执行循环直接进入回收分支，同样必须释放 KV 与压缩状态。

两条路径都要记录 finish reason；差别在于是否走完采样与流式拼装。

前缀缓存命中

确认命中的 key 包含 tokenizer/template、adapter、多模态预处理等必要上下文；区分复用 token KV 与模型独有压缩/索引状态是否都可复用。

抢占与重算

显存压力可能触发暂停、驱逐或 prefill 重算；核查压缩 state、逻辑位置和 cache block 映射能否完整恢复。

取消与流式返回

客户端断开后停止排队/后续 kernel 调度，避免 orphan request；验证 tool call、reasoning 段、finish_reason 的最终拼装。

9. 并行拓扑与精度路径复习

9.1 并行不是一个维度：先辨认切分对象

TP · 张量并行同一矩阵/注意力头按 rank 切；局部 GEMM 后常需 all-reduce / all-gather。追踪每个张量的切分轴与 collective。
EP · 专家并行专家放到不同 rank；router 后 dispatch tokens（常见 all-to-all），专家计算后 combine。关注 token 数不均衡与容量/负载均衡。
PP · 流水线并行连续层分给不同 stage；隐藏态跨 stage 发送，关注 bubble、microbatch、层间 cache/state 所属 stage。
DP / 副本模型副本处理独立请求批次；服务层调度和权重同步策略需区分推理与训练。

这些是并行概念示意，不代表当前笔记中的官方参考实现或具体运行命令必然启用了上述所有维度。以启动配置和实际通信 trace 为证。

10.1 V4.1 专项流程：Engram 查表与 DSpark 投机解码

Engram：稀疏条件记忆读写

从 token IDs 出发，按 n-gram / 配置窗口构造查表的 key。

key 经哈希 / 桶映射落到 memory slots —— 表本身是稀疏寻址的。

每一轮只会真正命中少数几行（图中 slot 1、3），其余行不参与计算。

稀疏 lookup 只读取命中的行及其 scale，主干 hidden 不经过这张表。

命中的记忆经投影融合回 hidden 维，再继续后续 attention / MoE。

复盘要点：参数总量不等于每 token 激活量，也不同于显存常驻量；还要算上 offload 的访问代价。

复盘要点：key 构造与冲突策略、表容量/命中率、读写 dtype 与 scale、CPU/offload 的访问代价；参数总量不等于每 token 激活量或显存常驻量。

DSpark：草稿、验证、接受/回退闭环

草稿阶段：用主模型上下文特征驱动草稿头，一次提出一整块 draft token。

主模型并行评估整块草稿 —— 不是把草稿再自回归跑一遍。

接受路径：前缀通过验证即可整体接纳，并额外获得一个 bonus token。

拒绝路径：定位第一个不匹配的 token，从这里开始全部作废。

状态同步：保留已接受 token 的 KV、回退草稿状态，然后回到下一轮草稿（闭环）。

必须分开测：草稿接受率、每轮接受 token 数、额外验证 FLOPs、缓存回滚正确性、端到端 tokens/s。只看 draft model 的生成速度无法说明 speculative decode 是否加速。
